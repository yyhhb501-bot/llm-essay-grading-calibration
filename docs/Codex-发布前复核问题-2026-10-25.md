## 必须修正或补验

### 1. P1：本地视觉模型验收不能覆盖 Worker 的模型选择

`site-server.js:339-340` 在共享配置存在时强制使用 `sharedConfig.model`；`worker/worker.js:219-220` 对未指定 model 的 vision 请求默认选 `glm-4v-flash`。新增关键流程测试用 Node 本地服务并断言视觉请求仍用 `glm-5.3-flash`，真实冒烟也不能证明正式 Worker 同样使用该模型。

这不是已证实的线上 OCR 故障，而是已证实的两端契约差异和验证缺口。统一共享文本/视觉模型配置与选择规则，新增 Worker 层无 model 的 vision 请求以及显式 model 请求断言，再通过普通账号正式验收拍照识别。不要沿用“共享模型可直接识图”作为生产环境已通过结论。

### 2. P1：发布包和回滚没有固定后端版本

`tools/prepare-site-release.js:139` 生成的 main 指向工作区 `worker/worker.js`，其 server 模块也从工作区导入；manifest 只记录 assets。`.agent/admin-release/wrangler.toml` 同样指向当前 worker 文件。

因此后续改动源码后，用同一个发布配置仍会部署不同后端；所谓回滚只保证旧静态资源，不能保证恢复旧 Worker。

应在发布目录固定 Worker 及依赖（或保存确定的 bundle），纳入哈希/提交版本校验；回滚固定真实旧版本或使用明确的 Cloudflare deployment/version ID。构建基线守卫还需覆盖 `server/`。验收：修改工作区后，已生成发布包不变，或部署前明确拒绝漂移；回滚不混用当前后端。

### 3. P2：错误邀请码测试会误报成功

`tools/test-key-flows.js:124` 调用 `ok(name, response.status, 403)`，但第 28 行 helper 只有两个参数，实际仅执行 `assert.ok(response.status)`。200、403、500 都为真，第三个参数被忽略。

改成 `response.status === 403` 或 `assert.equal(response.status,403)`，并验证模拟 201/500 时断言失败。现有账号套件的错误邀请码检查通过，因此本项是测试缺陷，不是已证实的注册绕过漏洞。

### 4. P2：回滚文档哈希拼写错误

请从回滚文件自动计算，更新生成器及现有发布包文档，避免健康回滚被误判失败。
